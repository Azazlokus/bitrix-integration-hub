# Bitrix Integration Lab — техническое задание

Учебный пет-проект: интернет-магазин на 1С-Битрикс (БУС), в котором собраны **все типовые виды интеграций**, встречающиеся в коммерческой разработке. Цель — практика, а не продакшен. Каждый этап самодостаточен и имеет критерии приёмки.

> Для Claude Code: работай поэтапно, по одному этапу за раз. После каждого этапа — коммит, обновление `docs/progress.md` и проверка критериев приёмки. Ничего не делай в ядре Битрикса.

---

## Архитектура (проект должен выглядеть как единая система, а не набор примеров)

- **Слои внутри модуля `lab.integration`:**
  - `Domain` — чистые сущности и интерфейсы (`OrderExporter`, `PaymentGateway`, `DeliveryCalculator`, `StockProvider`), без зависимостей от Битрикса;
  - `Application` — сценарии (use cases): «отправить заказ в CRM», «применить статус оплаты», «синхронизировать остатки»;
  - `Infrastructure` — адаптеры: Битрикс ORM/инфоблоки, клиенты Б24, 1С, ERP, платёжки, доставки, RabbitMQ;
  - `Presentation` — обработчики событий Битрикса, D7-контроллеры, агенты, CLI-команды. Только вызывают Application, без логики.
- Каждая внешняя система — порт (интерфейс) + адаптер. Подмена реального адаптера на mock — через конфиг DI (`.settings.php` → `services`, ServiceLocator D7).
- Все интеграции идут по одной схеме: событие → outbox → очередь → консьюмер → адаптер → журнал. Исключение — синхронные вызовы (расчёт доставки, создание платежа) с явным таймаутом и фолбэком.
- `docs/architecture.md`: C4-диаграмма уровня контейнеров и компонентов (Mermaid), схема потоков данных по каждой интеграции, ADR (Architecture Decision Records) в `docs/adr/` на ключевые решения: почему outbox, почему REST-мост с Laravel, а не прямой доступ к БД, почему свой обработчик оплаты и т.д.
- Проект должен быть понятен за 10 минут: README с картинкой архитектуры, `make up` + `make demo` (наполняет данными и прогоняет сквозной сценарий: заказ → оплата → доставка → CRM → 1С).

## 0. Правила проекта (обязательны для всех этапов)

- **Ядро не трогаем и не коммитим.** Весь свой код — только в `local/` (`local/modules`, `local/components`, `local/templates`, `local/php_interface`). Каталог `bitrix/` и `upload/` — в `.gitignore`.
- **Только D7 там, где это возможно**: неймспейсы, ORM (`DataManager`), `Bitrix\Main\Engine\Controller`, `EventManager`, `Config\Option`, `ServiceLocator`. Старое API (`CIBlockElement`, `CSaleOrder` и т.п.) — только если у D7 нет аналога, с комментарием почему.
- PHP 8.2+, `declare(strict_types=1)`, PSR-12, composer-автозагрузка (`local/composer.json`, подключение в `local/php_interface/init.php`).
- Вся логика интеграций — в своём модуле `local/modules/lab.integration` (namespace `Lab\Integration`). Тонкие обработчики событий → сервисы.
- Конфигурация внешних систем — через `.env` + `Config\Option` модуля, секреты не в коде.
- Логирование: PSR-3 (Monolog), отдельный канал на каждую интеграцию, логи в `local/logs/` (в `.gitignore`).
- Каждый вызов внешней системы: таймауты, ретраи с backoff, идемпотентность, запись в журнал интеграций (см. этап 2).
- Миграции БД и инфоблоков — через модуль `sprint.migration` (или свой механизм миграций в модуле), никаких ручных правок в админке, которые не воспроизводятся.
- Тесты: PHPUnit с бутстрапом Битрикса (`tests/bootstrap.php` подключает `prolog_before.php` с `NO_KEEP_STATISTIC`, `NOT_CHECK_PERMISSIONS`). Внешние системы в тестах — только моки.

## 1. Инфраструктура (docker-compose)

| Сервис | Назначение |
|---|---|
| `nginx` + `php-fpm` (8.2) | Битрикс (БУС, редакция «Бизнес», триал 30 дней) |
| `mysql` 8 | БД Битрикса |
| `redis` | кеш Битрикса и сессии |
| `rabbitmq` (с management UI) | очереди событий |
| `meilisearch` | внешний поиск по каталогу |
| `mailpit` | перехват почты |
| `mock-services` | один контейнер на PHP (Slim или голый PHP), эмулирует внешние системы: платёжку, службу доставки, SMS-шлюз, ERP |
| `worker` | PHP CLI-консьюмеры очередей (тот же образ, что php-fpm) |
| `keycloak` (опционально, профиль `sso`) | OIDC-провайдер для SSO |

- `Makefile` с командами: `up`, `down`, `shell`, `logs`, `test`, `migrate`, `worker`, `tunnel`.
- `.env.example` со всеми переменными.
- Для входящих вебхуков из облачного Битрикс24 — туннель (cloudflared или ngrok), команда `make tunnel`.

**Ручные шаги (делает человек, Claude Code описывает их в README):**
1. Скачать `bitrixsetup.php` с сайта 1С-Битрикс, положить в webroot, пройти мастер установки (редакция «Бизнес», демо интернет-магазина можно не ставить).
2. Завести бесплатный облачный портал Битрикс24, создать входящий вебхук и локальное приложение.

**Приёмка:** `make up` поднимает всё; сайт открывается; кеш Битрикса работает через Redis (настроено в `bitrix/.settings_extra.php`, генерация этого файла — скриптом из репо); `make test` запускает пустой набор тестов с бутстрапом Битрикса.

## 2. Каркас модуля и журнал интеграций

**Приёмка:** модуль ставится/удаляется из админки без ошибок; любой исходящий запрос отображается в журнале.

## 4. Обмен с 1С по протоколу CommerceML

Эмулируем 1С, т.к. реальной 1С нет.

- Скрипт-эмулятор в `mock-services` (или CLI-команда в `tools/`), который проходит **полный протокол обмена** со штатным `/bitrix/admin/1c_exchange.php`:
  - `type=catalog`: `checkauth` → `init` → `file` (передача `import.xml` и `offers.xml`, в т.ч. zip) → `import` (повторять до `success`).
  - `type=sale`: `checkauth` → `init` → `query` (забрать заказы) → `success` → `file` (вернуть статусы заказов).
- Генератор тестовых CommerceML-файлов (товары, свойства, SKU, цены, остатки) с настраиваемым объёмом.
- Обработчики событий импорта (`catalog:OnSuccessCatalogImport1C`, `iblock:OnBeforeIBlockElementUpdate` и т.п.) для своей постобработки: например, сброс тегированного кеша, отправка изменений цен в очередь.

**Приёмка:** эмулятор загружает 1000 товаров с SKU, ценами и остатками; повторная загрузка обновляет, а не дублирует (по XML_ID); заказ с сайта уходит в «1С», статус «оплачен» возвращается и применяется.

## 5. Свой REST API сайта (Битрикс как провайдер)

- D7-контроллеры (`Bitrix\Main\Engine\Controller`) в модуле, роутинг через `local/routes/api.php` (новый роутинг D7, подключение в `.settings.php`).
- Эндпоинты: `GET /api/v1/products` (пагинация, фильтры), `GET /api/v1/products/{id}`, `POST /api/v1/orders`, `GET /api/v1/orders/{id}`.
- Аутентификация по API-ключу (заголовок) + отдельно вариант с JWT. Префильтры: метод, CSRF выключен для API, rate limit (Redis).
- Единый формат ошибок, валидация входных данных, OpenAPI-спецификация в `docs/openapi.yaml`.

**Приёмка:** спецификация валидна; e2e-тест через HTTP создаёт заказ; без ключа — 401; при превышении лимита — 429.

## 6. Битрикс24: CRM-интеграция

Используем облачный портал (бесплатный тариф).

1. **Входящий вебхук (сайт → Б24):** при создании заказа на сайте — найти или создать контакт (дедупликация по телефону/email), создать сделку с товарными позициями (`crm.deal.add`, `crm.deal.productrows.set`). Использовать `batch` для пакетных вызовов. Учитывать лимиты запросов (2 req/s) — очередь + троттлинг.
2. **Исходящие события (Б24 → сайт):** подписка на `ONCRMDEALUPDATE`; при переводе сделки в стадию «Оплачено»/«Отменено» — меняется статус заказа на сайте. Проверка `application_token`, идемпотентность.
3. **Локальное приложение с OAuth 2.0:** установка, хранение и автообновление `access_token`/`refresh_token` (ORM-таблица), обработка `expired_token`.
4. **Встройка (placement):** вкладка в карточке сделки `CRM_DEAL_DETAIL_TAB`, показывающая данные заказа с сайта (история, состав, ссылки).
5. **Робот / активити бизнес-процесса:** зарегистрировать робота `bizproc.robot.add` «Проверить остаток на сайте», который вызывает API сайта и возвращает результат в БП.
6. **Синхронизация каталога** в товарный каталог Б24 (`catalog.product.*` или `crm.product.*`) по расписанию, инкрементально.

**Приёмка:** заказ → сделка с позициями в течение минуты; смена стадии в Б24 меняет статус на сайте; токены сами обновляются; вкладка и робот работают в портале.

## 9. Очереди и асинхронность (RabbitMQ)

- Обработчики событий Битрикса (`sale:OnSaleOrderSaved`, изменение товара, смена статуса) **не ходят во внешние системы напрямую**, а пишут в outbox (этап 2) в той же транзакции.
- Релей outbox → RabbitMQ (CLI-команда или агент на cron).
- Консьюмеры в контейнере `worker` (CLI-скрипты с бутстрапом Битрикса): отправка в Б24, в ERP, в поиск. Dead-letter queue, ограничение ретраев, graceful shutdown.
- Агенты Битрикса перевести на cron (`BX_CRONTAB_SUPPORT`, `cron_events.php`) — описать и настроить в docker.

**Приёмка:** при выключенном Б24 заказы копятся в очереди и доотправляются после включения; «битое» сообщение уходит в DLQ, а не блокирует очередь.

## 10. Внешняя ERP / учётная система (REST + файловый обмен)

Альтернатива 1С, чтобы потрогать «чужой» API.

- Mock-ERP в `mock-services` с REST API (пагинация курсором, OAuth2 client credentials) и SFTP/папкой с CSV.
- Импорт остатков по API раз в 5 минут (дельта по `updated_since`) и полная сверка ночью из CSV.
- Маппинг внешних ID (ORM-таблица соответствий), обработка конфликтов.

**Приёмка:** остатки на сайте совпадают с ERP после сверки; импорт 10 000 позиций укладывается в разумное время (батчи, без `GetList` в цикле).

## 15. Мост с Laravel (Laravel ↔ Битрикс)

Частый кейс в вакансиях: Битрикс как витрина/CMS + Laravel как отдельный сервис (админка менеджеров, личный кабинет B2B, сервис отчётов).

- Отдельное приложение на Laravel 11+ (`apps/laravel-hub`, свой контейнер), которое:
  - вариант А: работает только через REST API сайта (этап 5) — основной, «правильный» вариант;
  - вариант Б: читает БД Битрикса напрямую через отдельное подключение (read-only, Eloquent-модели поверх `b_sale_order` / HL-таблиц) — для отчётов;
  - вариант В: artisan-команда, подключающая ядро Битрикса (prolog), — показать, почему так делать можно, но не стоит.
- Laravel слушает те же очереди RabbitMQ (этап 9) и строит B2B-отчёт по заказам (Laravel Queue / консьюмер).
- Сравнить подходы в `docs/laravel-bridge.md` (плюсы, минусы, когда что выбирать).

**Приёмка:** Laravel-приложение показывает список заказов через API сайта и отчёт из очереди; сравнение подходов задокументировано.
