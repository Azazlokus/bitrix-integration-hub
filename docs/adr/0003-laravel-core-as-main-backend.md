# 0003. Laravel Core — основной бэкенд, Битрикс — витрина

- **Статус:** Accepted
- **Дата:** 2026-11-08
- **Этап ТЗ:** все (перестройка roadmap)

## Контекст

Исходное ТЗ строит интеграции вокруг Битрикса, а внешние системы эмулирует моками (`mock-services`), Laravel появляется только на этапе 15. Владелец проекта хорошо знает Laravel и хочет:

- отрабатывать интеграции на задачах, похожих на боевые;
- видеть каждый вид интеграции на знакомой стороне — Laravel.

## Рассмотренные варианты

1. **Оставить ТЗ как есть, Laravel — только этап 15.**
   - Плюсы: без отклонений от ТЗ.
   - Минусы: внешние системы — игрушечные моки; знание Laravel не помогает понять интеграции.
2. **Laravel — внешняя система, заменяющая mock-services** (ERP, платёжка, доставка).
   - Плюсы: реалистичнее моков.
   - Минусы: Laravel изображает чужие продукты (ЮKassa, СДЭК) — нереалистично, бизнес-логики нет.
3. **Laravel — основной бэкенд компании (PIM, OMS, B2B), Битрикс — витрина.**
   - Плюсы: так устроены многие коммерческие проекты. Почти все виды интеграции естественно ложатся на пару «Битрикс ↔ Laravel», а сторонние сервисы (эквайринг, доставка, SMS, маркетплейс, Б24) остаются сторонними.
   - Минусы: заметное отклонение от ТЗ, больше кода (полноценное приложение Laravel).

## Решение

Вариант 3 (выбор владельца). Детали — [roadmap.md](../roadmap.md).

- Laravel 13: на 2026-11-08 Laravel 11 — EOL, у 12 закончилась активная поддержка. Стек: Filament 5, Passport 13, Scout 11, Pest 5, Larastan 3, PostgreSQL 18.
- С Битрикс24 интегрируется сайт на Битриксе (как в ТЗ): это ключевой навык Битрикс-разработчика.
- Передача заказов в OMS — один порт `OrderExporter` и адаптеры `commerceml` и `queue`, выбор через DI. Одна бизнес-операция показывает два вида интеграции без дублирования логики.
- Laravel играет роль «1С» в обмене CommerceML. Мастер-данные каталога находятся в Laravel, поэтому выгрузка из учётной системы через штатный `1c_exchange.php` — реальная практика.

## Последствия

- Источник истины по этапам — `docs/roadmap.md`. Раздел 0 ТЗ (правила) действует для кода Битрикса.
- Появляются контейнеры `core` и `postgres`, каталог `contracts/` с межсистемными контрактами и контрактные тесты с обеих сторон.
- `mock-services` сокращаются до действительно сторонних сервисов.
- Этап 15 ТЗ распадается: вариант А → этап 10 roadmap (`bitrix-api`), варианты Б/В → этап 17 (`anti-patterns`).
